# モード定義

このファイルは `japanese-tech-writing` スキルの3つの運用モード（生成、推敲、公開前チェック）を、実行手順として定義する。`SKILL.md` から読み込まれる。モードの選択自体は `SKILL.md` が担い、このファイルは選ばれた後の具体的な手順だけを記述する。

各モードは [rules.md](rules.md)（文章規範の本体）、[checklist.md](checklist.md)（severity 方式の点検リスト）、[style-profiles.md](style-profiles.md)（文書の型ごとの例外）を参照する。

## モードA：生成

新しい日本語技術文書を最初から書くときに使う。

1. **対象を確定する。** 何を書くか（章、記事、解説）、誰に向けて書くか（読者の役割や前提知識）、どれくらいの分量かを確認する。指定がなければ最小限だけ質問し、憶測で埋めない。
2. **文書の型を選ぶ。** 技術書の章、API リファレンス、技術ブログ、翻訳解説のどれに近いかを判断し、[style-profiles.md](style-profiles.md) にその型固有の例外があれば適用する。例外が定義されていない型は [rules.md](rules.md) をそのまま適用する。
3. **[rules.md](rules.md) の全規範を、書きながら適用する。** 下書きを先に書いて後から直す二段構えにしない。一文を書く時点で、整形、段落と論証の構成、論証の厳密さ、読み手の負荷の管理、視点と語り、演出の抑制、LLM っぽい表現の禁止、冗長の排除、見出しの付け方、読者への誠実さのすべてを満たす形で書く。
4. **書き終えたら通読し、自己点検する。** 特に、段落単位で論理を追えるか（一段落一トピックか、段落冒頭で内容が分かるか）と、「LLM っぽい表現の禁止」セクションに挙げた言い回しが紛れ込んでいないかを重点的に見る。
5. **違反が見つかればその場で直してから提示する。** 規範の解説を本文に混ぜない。読者に見せるのは本文だけである。

生成モードでは、モードB の4パスやモードC のチェックリストを別途通す必要はない。最初から規範に沿って書けば、それらは形式上の通過点になる。

## モードB：推敲

既存の下書きを受け取り、規範に沿って直すときに使う。

1. 対象テキストを受け取る（ファイルパスまたは貼り付け）。
2. 下記の4パスを、**この順序のまま**適用する。順序を入れ替えたり、パスを飛ばしたりしない。前のパスの修正が後のパスの判断を変えることがあるため、後段から手を付けると同じ箇所を何度も書き直すことになる。
3. 4パスが終わったら、naturalize-ja への引き継ぎ（後述）を行う。
4. 修正版を提示し、直した箇所とどの規範に基づくかを簡潔に示す。
5. 意味が一意に決まらず、直すと内容が変わりうる箇所は、直さずに指摘してユーザーに判断を仰ぐ。

### パス1：論証と厳密さ

最初に直す。ここが崩れていると、後続のパスで整えた文章が結局作り直しになる。

- [rules.md](rules.md) の「論証の厳密さ」セクション全体（根拠のない推量表現の削除、異なるものを同一視しない、複数要因を単一原因に還元しない、機構を伴わない因果主張、絶対化の回避、術語の地位の一貫性など）。
- 「段落と論証の構成」セクションのうち、論証の順序と自己矛盾に関わる項目（論証を一方向に進める、結論を一度だけ置く、誤った解釈を先回りして否定する、「AではなくB」に根拠を添える、譲歩を著者の声で因果として断定しない、山場の情報を先出ししない、否定する命題を「」で正確に書く）。同セクションの残り（一段落一トピックなど、構造そのものに関わる項目）はパス2で扱う。この節を2パスに割っているのは、論証の順序や整合性の誤りは内容そのものの誤りであり、構造の整え方より先に直す必要があるためである。
- 「読者への誠実さ」セクション全体。確認していないことを確認したかのように書いていないか、作為的に見える例を隠していないかは事実主張の正確さの問題であり、構成や語彙の問題ではないため、ここで扱う。

### パス2：構成と段落

論証の内容が固まった後に、それを収める構造を直す。

- 「段落と論証の構成」セクションのうち、構造に関わる項目（一段落一トピック、段落冒頭で内容が分かるようにする、接続表現で前段落との関係を示す、例への弁明を節の冒頭にまとめる、前方参照を段落末や節末に置く）。
- 「見出しの付け方」セクション全体。見出しは段落と並ぶ構造要素なので、このパスで一緒に直す。

### パス3：読み手の負荷と冗長

構造が固まった後に、読者の負担を減らす。

- 「読み手の負荷の管理」セクション全体。
- 「冗長の排除」セクション全体。

### パス4：表層（最後）

内容と構造が固まってから、最後に表層を整える。ここを先に直すと、後のパスでの書き直しによって無駄になる。

- 「整形」セクション全体（ダッシュ類、中黒、区切り線を使った見出し、太字強調、脚注）。
- 「視点と語り」セクション全体。能動態か受動態か、主語に何を選ぶか、術語や訳語の選び方は語句レベルの選択であり、論証の正しさそのものには関わらないため、ここで扱う。
- 「演出の抑制」セクション全体。
- 「LLM っぽい表現の禁止」セクション全体。

### パス完了後：naturalize-ja への引き継ぎ

4パスが終わった時点で、[rules.md](rules.md) に基づく文章設計、論証、構成の観点からの推敲は完了している。

ここから先の「AI っぽい語彙の検出と置換」はこのスキルでは行わない。**`naturalize-ja` スキルに引き継ぐ。** AI 臭語彙の正本は `naturalize-ja` の `references/ai-japanese-patterns.md` であり、このスキルはそれを持たない。このスキルの「LLM っぽい表現の禁止」セクションは、論証や構成に絡む言い回し（予告と総括、正面から系など）を扱う抜粋にすぎない。4パスを終えたテキストは、そのまま `naturalize-ja` に渡す。

## モードC：公開前チェック

文書を公開する前に、規範への違反を洗い出して報告するときに使う。**修正はここでは行わない。**

1. 対象テキストを受け取る。
2. [checklist.md](checklist.md) の各項目に対して、対象テキスト全体を照合する。文書の型に [style-profiles.md](style-profiles.md) の例外が定義されていれば、その例外を踏まえて判定する。
3. 見つかった違反を、checklist.md が定める severity（BLOCKER、IMPORTANT、TASTE の3段階）ごとに分類する。
4. 報告は、まず BLOCKER、次に IMPORTANT、最後に TASTE という順序で示す。各項目には該当箇所と、どの規範に違反しているかを添える。
5. **修正は自動で適用しない。** 違反の一覧と根拠を示すところまでを行い、直すかどうかと直し方はユーザーに委ねる。
6. checklist.md に総合判定の基準が定義されていれば、それに従って結論を一行添える。定義されていない場合は、BLOCKER が一件でもあれば「公開前に対応が必要」、BLOCKER がなく IMPORTANT のみであれば「公開は可能だが改善の余地がある」、TASTE のみまたは違反なしであれば「公開可」と記す。
